1. `scripts/run_scan.py`의 매매 조건·점수화·TOP10 산출 로직을 **변경하지 않는다.** 외부에서 **import**만 한다.
2. **DB 테이블 구조와 기존 데이터** 변경 금지. 신규 테이블도 만들지 않는다(v0.2).

5. 기존 TOP10 결과가 단 1종목이라도 바뀌면 안 된다.
6. `.env.local` 출력·수정·커밋 금지.
7. 키움 API 연동·자동주문 기능 금지. 화면은 **참고용 표·라벨**만.
8. 금지 표현 사용 금지: 매수하세요 / 매도하세요 / 목표가 / 추천매수가 / 급등 예상 / 상한가 후보 / 자동매수.

## 3. `scripts/scan_dump.py` — 역할 설계

### 목적
- 전 종목에 대해 `analyze()`를 한 번 더 실행해 **전체 진단 결과**를 JSON으로 떨굼.
- 핵심 산출물: 바닥 U턴 후보 / 추격 위험 강화 / 종목별 단계 라벨.

### 입력
- Supabase 읽기: `stocks`, `daily_prices`, `market_indices`, `news_risks` (각각 `run_scan` 안에 있는 fetch 함수를 그대로 호출)
- 옵션: `--report-type {daily,weekly}` (기본 daily, 골든크로스 윈도우 5/10 일치)

### 처리 (run_scan의 분석을 그대로 재사용, 결과는 저장만 다르게)
1. `import` 대상(모두 기존 함수, 호출만 함):
   - `from run_scan import analyze, fetch_stocks, fetch_all_prices, fetch_market_index_data, fetch_news_risks`
2. 데이터 로드 — **`fetch_all_prices(use_cache=True)`** 호출하여 1차/2차 개선의 캐시를 그대로 활용.
3. 종목별 `analyze(df, market_cap, market_above_ma60=..., golden_window=..., market_20d_return=..., sector_20d_return=...)` 호출.
4. 결과를 다음 단계 라벨로 분류(이미 운영 표현)
   - `golden_days_ago == None` 또는 골든크로스 직전 → **바닥 관찰** (단, `cond_uturn_ok` 충족 시만)
   - `0 ≤ golden_days_ago ≤ 1` → **U턴 시도**
   - `2 ≤ golden_days_ago ≤ 5` → **U턴 확인**
   - `golden_days_ago ≥ 6` → **추세전환 후보**
5. **바닥 U턴 후보의 강화 조건**(단순 낙폭 종목 배제)
   - U턴 검증 통과(`cond_uturn_ok`: 최근 60일 중 60일선 아래 ≥10일)
   - 20일 평균거래대금 회복(예: 직전 20일 평균보다 최근 5일 평균이 일정 비율 이상)
   - 60일선 상승 시작 or 종가 60일선 근접/돌파
   - 후행스팬·구름 조건 부분 충족 등 가산점 신호
   - → 위 조건들의 **충족 수**를 점수가 아닌 **체크리스트**로 표시(점수화는 run_scan의 영역이라 별도)
6. **추격 위험 강화 진단**(현재 `final_grade=CHASE_RISK`보다 세분):
   - 이격도 +20% 이상 / 갭상승 후 음봉 누적 / 60일선 대비 +30% 등 신호를 **OR 조합**으로 라벨

### 출력 (JSON 1개 — 덮어쓰기)
- 경로: `logs/sidecar/scan_dump_latest.json` (가장 최근만, 작고 빠르게)
- 보존: `logs/sidecar/history/scan_dump_<YYYY-MM-DD>_<daily|weekly>.json` (선택, 히스토리)
- 스키마 예시(요지):
```json
{
  "generated_at": "2026-06-02T12:34:56+09:00",
  "report_type": "daily",
  "base_date": "2026-05-22",
  "market": { "kospi_above_ma60": true, "kosdaq_above_ma60": true,
              "kospi_20d_return": 24.27, "kosdaq_20d_return": -0.15 },
  "candidates_bottom": [   /* 바닥 U턴 분류 */
    { "ticker": "...", "name": "...", "stage": "바닥 관찰",
      "checks": { "uturn_ok": true, "value_recovering": true,
                  "ma60_rising": false, "lagging_ok": true, "cloud_red": false },
      "close": 12345, "ma60": 11800, "disparity_pct": 4.6,
      "days_below_ma60_60d": 22,
      "evidence": ["U턴 검증 충족(아래 22일)", "거래대금 회복", "후행스팬 정상"] }
  ],
  "chase_risk_strong": [   /* 추격 위험 강화 라벨 */
    { "ticker": "...", "reasons": ["이격 +28%", "갭 상승 후 음봉"] }
  ],
  "all_stage_labels": [    /* 종목 전부의 단계 라벨 (옵션) */
    { "ticker": "...", "stage": "U턴 확인", "final_grade_from_run_scan": "A" }
  ]
}
```

### 보호 보증
- `run_scan.py` 무수정. `analyze()` 호출 결과를 **그대로** 분류만.
- DB write 없음. 캐시 사용으로 부담 없음.
- `final_grade`/점수는 **참고만** 표시(재계산하지 않음 → 결과 변경 0).

## 4. `scripts/sector_dump.py` — 역할 설계

### 목적
- 섹터(업종) 강도와 그 안의 **진짜 주도주 후보 / 후발주 관찰**을 JSON으로 떨굼.

### 입력
- Supabase 읽기: `stocks(ticker, sector, market_cap)`, `daily_prices`, `market_indices`
- 옵션: `--top-sectors N`(기본 5), `--min-stocks-per-sector N`(기본 5)

### 처리
1. `from run_scan import fetch_all_prices, ...` (캐시 재사용)
2. 종목별 20거래일 수익률 계산(이미 `run_scan` 내부 산식과 동일하게).
3. **섹터별 평균 20일 수익률** 집계 → 시장(`market_indices` 20일 수익률) 대비 상대강도.
4. 강한 섹터 상위 N개 추출.
5. 각 강한 섹터 안의 종목 분류:
   - **진짜 주도주 후보**: 종가가 최근 60일 고가의 90% 이상 + 20일 거래대금 일정 이상 + 60일선 위 + 이격 한계 이내
   - **후발주 관찰**: 같은 섹터인데 위 조건 미달이나, 거래대금 증가 + 60일선 접근 중
   - **추격 위험**: 같은 섹터인데 이격 +20% 이상 또는 단기 급등 후 변동성 큼
   - **조건 부족 / 보유자 대응**: 그 외
6. 시장 전체 흐름(KOSPI/KOSDAQ 60일선)과 결합해 헤더에 **강세 흐름 / 중립 흐름 / 약세 흐름** 라벨 표기(이미 `/market`에서 쓰는 산식과 동일).

### 출력 (JSON 1개 — 덮어쓰기)
- 경로: `logs/sidecar/sector_dump_latest.json`
- 보존: `logs/sidecar/history/sector_dump_<YYYY-MM-DD>.json` (선택)
- 스키마 예시(요지):
```json
{
  "generated_at": "2026-06-02T12:34:56+09:00",
  "market_flow": "강세 흐름",
  "kospi_20d_return": 24.27,
  "kosdaq_20d_return": -0.15,
  "sectors_strong": [
    {
      "sector": "전기전자",
      "sector_20d_return": 8.1,
      "market_relative_strength": 8.1 - 12.0,
      "n_stocks": 87,
      "leaders": [
        { "ticker": "...", "name": "...", "close": 12345,
          "rel_strength": 12.3, "value_20d_eok": 250.4,
          "near_high_pct": 96.2, "label": "진짜 주도주 후보",
          "evidence": ["전고점의 96.2%", "거래대금 250억"] }
      ],
      "followers": [
        { "ticker": "...", "name": "...", "label": "후발주 관찰",
          "evidence": ["같은 섹터 강세", "60일선 접근 중", "거래대금 증가"] }
      ],
      "chase_risk": [
        { "ticker": "...", "label": "추격 위험", "evidence": ["이격 +24%"] }
```

### 보호 보증
- DB write 없음. 같은 캐시(B안) 재사용.
- 결과 라벨링은 **읽기 결과의 가공**이며 `analyze()` 자체는 호출하지 않거나 호출하더라도 출력만 사용.

## 5. JSON 저장 위치 후보와 장단점

| 후보 | 장점 | 단점 | 평가 |
|------|------|------|------|
| **`logs/sidecar/`** | 이미 `.gitignore`(`/logs/`)로 제외됨 — 사고 0. 권한 단순. | 정적 서빙 불가 → Next.js 서버 컴포넌트에서 `fs.readFile`로 읽어야 함. | ✅ **권장** |
| `public/data/sidecar/` | Next.js에서 정적 fetch 가능. | `public/`은 git 추적 폴더 → `.gitignore`에 별도 패턴 추가 필요. 사고 시 민감 산출물이 깃에 올라갈 위험. | △ |
| `data/sidecar/` (신규) | 의미 명확. | 새 폴더 + `.gitignore` 갱신 필요. logs와 의미 분리하는 가치는 크지 않음. | △ |

**결론:** `logs/sidecar/`에 두고 Next.js 서버 컴포넌트가 `fs.readFile(path.join(process.cwd(), 'logs/sidecar/...'))`로 직접 읽는다.

**Next.js 읽기 코드(설계 예시 — v0.2 구현 시):**
```ts
// 서버 컴포넌트에서
import { readFile } from 'fs/promises';
import path from 'path';

async function readSidecar(name: string) {
  try {
    const p = path.join(process.cwd(), 'logs', 'sidecar', name);
    const buf = await readFile(p, 'utf-8');
    return JSON.parse(buf);
  } catch {
    return null;  // 파일 없거나 손상 → graceful 빈 상태
  }
}
```

파일이 없거나 손상되면 **빈 상태로 graceful 표시**(에러로 중단 금지).

## 8. `/kiwoom-helper` 고도화 방향 (v0.2)

### 현재(v0.1) → 고도화(v0.2)
- 현재: 최신 `reports` 1건의 `scan_results`만 보여줌.
- 고도화: **사이드카에서 추가된 종목**(바닥 U턴 후보·진짜 주도주 후보)까지 같은 표 형식으로 통합 표시.

### 가격 라벨(불변, 표현 원칙 그대로)
- **돌파 확인가** — 60일 고가 추정 또는 단기 전고점
- **눌림 확인가** — 10일선 / 20일선(눌림 1차 / 2차)
- **위험 기준가** — 손절선 참고(최근 20일 저가와 60일선 중 높은 쪽)
- **추격 주의가** — 60일선 대비 +20% 임계

### v0.2 추가 항목 (라벨 신설 없음, 같은 4가지 라벨로 표현)
- 종목 옆 단계 라벨(바닥 관찰 / U턴 시도 / U턴 확인 / 추세전환 후보)
- 분류 라벨(진짜 주도주 후보 / 후발주 관찰 / 기회 후보 / 추격 위험 / 조건 부족 / 보유자 대응)
- **복사 친화 텍스트 박스**(클릭하면 키움 입력용 한 줄 텍스트가 선택됨) — 자동주문 아님, 안내 박스 그대로 상단 표기 유지.

### 절대 금지
- "추천매수가", "목표가", "이 가격에 사세요" 같은 표현 일절 금지.
- 자동주문·API 전송 기능 없음.

## 11. 위험한 수정 지점

| 지점 | 위험 | 회피 방법 |
|------|------|-----------|
| `run_scan.py` 함수 시그니처 변경 유혹 | TOP10 결과 변경 위험 | 사이드카는 **호출만**. 시그니처 변경 금지. 필요한 새 산식은 사이드카 내부 함수로. |
| `fetch_all_prices` 캐시와 동시 접근 | 캐시 파일 동시 쓰기 충돌 | v0.2 사이드카는 **`use_cache=True`만 사용**(읽기/생성 모두 안전). 캐시 무효화 책임은 `run_daily.bat` ② 단계의 기존 메커니즘 그대로. |
| 신규 테이블 추가 욕구 | DB 스키마 변경 = 보호 원칙 위반 | v0.2는 JSON만. 테이블 추가 결정은 v0.3 이후 별도 안건. |
| `run_daily.bat`에 사이드카를 무리하게 끼우기 | 9단계 흐름 손상 + 실패 시 전체 중단 위험 | 별도 `run_sidecar.bat` 또는 수동 실행으로 **먼저 검증.** 안정화 후 v0.3에서 배치 통합 검토. |
| Next.js의 `fs.readFile` 사용 | 빌드/배포 환경 차이 | 개인 PC 로컬 실행 전제(현 운영). `try/catch`로 graceful 폴백. |
| 화면 라벨에 금지 표현 혼입 | 원칙 위반 | 사이드카 출력에도 "매수/매도/목표가" 등 금지어 자동 grep 검사 추가. |

## 14. 권장 개발 순서

각 단계 끝마다 **회귀 검증 + 짧은 보고 + 사용자 승인** 후 다음 단계.

1. **사전 점검** — v0.1 회귀 없음 확인(`npm run build`, 기존 화면 진입).
2. **scan_dump.py 초안** — `analyze()` import해서 단계 라벨/바닥 후보만 출력. **TOP10 결과 변경 0** 검증.
3. **sector_dump.py 초안** — 섹터별 강도 + 진짜 주도주/후발주 라벨만 출력. 분류 결과는 작은 표본부터.
4. **사이드카 단독 실행 검증** — `.venv\Scripts\python.exe scripts\scan_dump.py` 단독 수행 후 JSON 생성 확인. 결과 표본 5~10개로 사람 검수.
5. **`/bottom-watch` 화면** — `fs.readFile` 기반. 파일 없을 때 빈 상태 표시 확인.
6. **`/leaders` 화면** — 같은 패턴.
7. **`/kiwoom-helper`·`/journal` 카드 보강** — 골격 유지, 카드 표시 항목만 추가.
8. **최종 회귀 검증** — TOP10 동일성, 기존 화면 정상, 새 화면 정상.
9. **커밋(선별)** — 코드/문서만 추가, 노이즈 제외. 푸시.

## 16. 롤백 기준

다음 중 **하나라도** 발생하면 즉시 롤백.

- TOP10 결과(daily 또는 weekly)가 한 종목이라도 달라짐.
- `scan_results`/`reports`/`backtest_results` 행수가 사이드카 실행으로 바뀜.
- `run_scan.py`/`run_daily.bat`/`run_backtest.py` 파일이 변경됨.
- 사이드카 출력 또는 새 화면에 금지 표현이 검출됨.
- `npm run build` 실패.
- 기존 화면 7개 또는 v0.1 화면 4개에서 회귀 발생(빈 화면·콘솔 에러·DB 오류 등).

### 롤백 방법
1. 새 화면 파일 삭제(`app/bottom-watch/`, `app/leaders/` 디렉터리).
2. 기존 v0.1 화면(`/kiwoom-helper`, `/journal`)에서 v0.2 보강 부분 되돌리기(`git restore app/kiwoom-helper/page.tsx app/journal/page.tsx`).
3. 사이드카 스크립트 삭제(`scripts/scan_dump.py`, `scripts/sector_dump.py`).
4. `logs/sidecar/` 폴더 정리(필요 시 `rmdir /s /q logs\sidecar`).
5. 마지막 안전 지점(`112702e` 또는 v0.2 시작 직전 커밋)으로 `git restore`.
