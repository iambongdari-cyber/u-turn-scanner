## 4. `run_sidecar.bat` 동작 요약

### 헤더
```
============================================
 U-Turn Scanner Sidecar
 Start: <date> <time>
============================================
run_daily.bat과 독립적으로 사이드카 2종만 실행합니다.
결과는 logs\sidecar\ 아래 JSON 파일로 떨어집니다.
한 단계가 실패해도 다음 단계는 계속진행하며,
run_daily.bat과 달리 전체 시스템에는 영향이 없습니다.
```

### 실행 환경 준비
- `cd /d "%~dp0"` — 배치 파일이 위치한 폴더(프로젝트 루트)를 작업 디렉터리로 설정. 더블클릭·터미널 어디에서 호출되든 일관된 동작.
- `mkdir logs` / `mkdir logs\sidecar` — 폴더가 없으면 생성. 이미 있으면 무시.
- `set "PY=.venv\Scripts\python.exe"` — 파이썬 경로 일원화.

### 실행 흐름
| 단계 | 명령 | 실패 처리 | 상태 변수 |
|------|------|----------|-----------|
| **[1/2] 바닥 사이드카** | `"%PY%" scripts\scan_dump.py` | 실패 시 `[WARN]` 표시 후 다음 단계 진행 | `SCAN_STATE` = 성공 / 실패-계속진행 |
| **[2/2] 섹터 사이드카** | `"%PY%" scripts\sector_dump.py` | 실패 시 `[WARN]` 표시 후 최종 파일 확인으로 계속 | `SECTOR_STATE` = 성공 / 실패-계속진행 |

### 최종 파일 확인 (실제 결과 표시)

```
============================================
  scan_dump_latest.json   : 존재 / 없음
  sector_dump_latest.json : 존재 / 없음
```

## 5. 실패 처리 방식

### 핵심 원칙
- `run_daily.bat`의 WARN 단계(`[1/9]` 종목 마스터·`[7/9]` 백테스트·`[8/9]` 알림 생성)와 **동일한 패턴**.
- `if errorlevel 1 ( ... ) else ( ... )` 분기로만 처리하며 **`goto :end` 호출 없음**.
- 한 단계 실패가 다음 단계의 실행을 멈추지 않음.

### 정책 표

| 사건 | 처리 |
|------|------|
| `scan_dump.py` 실패 | 콘솔에 `[WARN] scan_dump.py 실패. sector_dump.py로 계속진행합니다.` 출력. `SCAN_STATE=실패-계속진행`. **`[2/2]` 진행** |
| `sector_dump.py` 실패 | 콘솔에 `[WARN] sector_dump.py 실패. 최종 파일 확인으로 계속진행합니다.` 출력. `SECTOR_STATE=실패-계속진행`. **최종 파일 확인 진행** |
| 두 단계 모두 실패 | 각각 `[WARN]`. 최종 파일 확인은 "없음"으로 표시. pause로 멈춤 |
| pause 직전 종료 회피 | 무조건 `pause >nul` — 더블클릭으로 실행해도 창이 사라지지 않음 |
| 화면(`/bottom-watch`·`/leaders`)에서의 graceful | 별도 처리 불필요. v0.2-2/3에 이미 구현된 graceful 안내(파일 없음 / 파싱 실패)가 흡수 |

### `run_daily.bat`와 핵심 차이
| 항목 | `run_daily.bat` | `run_sidecar.bat` |
|------|----------------|-------------------|
| 단계 수 | 9 | 2 |
| HARD 정책 | 일봉/지수/뉴스/스캔 4개 단계가 HARD (`goto :end`) | 0개 (전부 WARN) |
| WARN 정책 | 종목 마스터/백테스트/알림 | 모든 단계 |
| 웹서버 기동 | `[9/9]`에서 별도 창으로 띄움 | **없음** (단독 배치이므로) |
| 로그 기록 | `logs\run_daily.log`에 `run_logger.py`로 단계별 기록 | 없음 (단독 실행 — 콘솔에만 표시) |
| 실패 영향 | 전체 시스템에 영향 | 화면 graceful로 흡수, 영향 없음 |

> 단독 배치는 가볍게 유지하기 위해 `run_logger.py` 호출을 일부러 포함하지 않았습니다. v0.3-2의 `run_daily.bat` 통합 시에는 logger 호출을 포함할 예정입니다.

## 6. CRLF 확인 결과

### 현재 상태 (Write 도구 직후)
- `run_sidecar.bat` 줄바꿈 = **LF 단독 (CR 0개, lone LF 78개)**
- 이는 제 Write 도구의 일반적 동작으로, **사용자 PC에서 1회 정규화 필요**.

### 정규화 명령 (사용자 PC에서 1회)
```bat
.venv\Scripts\python.exe -c "d=open('run_sidecar.bat','rb').read().replace(b'\r\n',b'\n').replace(b'\n',b'\r\n'); open('run_sidecar.bat','wb').write(d)"
```

### 정규화 후 검증
```bat
.venv\Scripts\python.exe -c "d=open('run_sidecar.bat','rb').read(); print('CRLF:', d.count(b'\r\n'), 'lone LF:', d.count(b'\n')-d.count(b'\r\n'))"
```
- 통과 기준: `CRLF`가 줄수에 가깝고, `lone LF`가 **0**

### CRLF가 중요한 이유
- Windows cmd는 `.bat` 파일의 줄바꿈이 CRLF여야 `if/goto/블록` 등을 정상 파싱
- 이전 `run_daily.bat`에서 LF 사고로 창이 즉시 닫힌 경험 있음
- 이번 단계는 단독 배치라 사고가 나도 `run_daily.bat`에는 영향 없지만, **사용자가 더블클릭했을 때 배치가 동작하지 않으면 의미 없음**
