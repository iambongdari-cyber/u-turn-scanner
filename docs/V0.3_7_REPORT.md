# U-Turn Scanner — v0.3-7 "직전 스냅샷 대비 변화" 기능 보고서

> **작성 기준일:** 2026-06-04
> **선행 단계:** v0.3-6 사이드카 일별 스냅샷 보관 (`logs/sidecar/daily/` 생성 흐름 완료)
> **목표:** 매일 쌓이는 daily 스냅샷 중 **가장 최신 두 개(직전 스냅샷)** 를 비교해 **신규 진입 / 이탈 / 순위 상승·하락 / 점수 상승·하락 / 섹터 변화**를 한 화면(`/changes`)에서 확인. 분석 로직·DB·TOP10 산식·기존 JSON 구조·키움 모두 무변경.

> **v0.3-7 보정 (적용됨):** "어제 대비"라는 표현이 daily 스냅샷의 실제 상황(연속 날짜 보장 없음)과 맞지 않을 수 있어, 내부 로직·콘솔 메시지·화면 설명은 모두 **"직전 스냅샷 대비"** 로 정확화했다. 화면 큰 제목은 사용자 친숙도를 위해 "어제 대비 변화"를 유지하되, 바로 아래 부제와 강조 박스에 항상 비교 기준 날짜(예: `2026-06-04 vs 2026-06-02`)를 표시한다.

---

## 1. 작업 목적

v0.3-6에서 `logs/sidecar/daily/scan_dump_<YYYY-MM-DD>.json` 형태로 매일 스냅샷이 누적되도록 인프라가 완성됐다. 이번 v0.3-7은 그 인프라를 처음으로 활용해:

- **신규 진입**(오늘에는 있고 직전 스냅샷에는 없는 종목)
- **이탈**(직전 스냅샷에는 있고 오늘에는 없는 종목)
- **순위 상승 / 하락**(같은 종목의 직전→오늘 순위 변화)
- **점수 상승 / 하락**(`score_from_run_scan` 비교, 임계 ±0.5)
- **섹터 변화**(`sector` 필드 변화)

를 별도 JSON(`logs/sidecar/change_dump_latest.json`)에 1회 계산하고, `/changes` 화면에서 표·요약카드로 보여준다.

**중요:** v0.3-7은 비교 화면만 추가하며, 사이드카 latest JSON 구조도 그대로 유지한다. `change_dump_latest.json`은 *비교 결과 저장소*이지 분석 결과가 아니다.

### 1-1. 용어 정확화 (v0.3-7 보정 핵심)

| 영역 | 표현 |
|---|---|
| 화면 큰 제목 (`<h1>`) | "어제 대비 변화" (유지 — 사용자 친숙도) |
| 화면 부제·메타·표 컬럼 | **"직전 스냅샷 대비"**, "직전 순위", "직전 점수", "직전 N (어제 값)" |
| 화면 상단 강조 박스 | "비교 기준: `<today_date> vs <previous_date>`" (필수 노출) |
| 스크립트 콘솔 로그 | `compare 2026-06-04 vs 2026-06-02 (previous snapshot): ...` |
| JSON 필드(정식) | `today_date`, `previous_date`, `today_path`, `previous_path`, `compare_label` |
| JSON 필드(호환 유지) | `yesterday_date`, `yesterday_path` 도 같은 값으로 함께 채움 |
| 부족 시나리오 메시지 | "직전 비교용 스냅샷이 부족합니다…" |

이유: daily 스냅샷이 주말/공휴일/실행 누락 등으로 **연속 날짜로 존재하지 않을 수 있다**. 예) 2026-06-02 → 다음은 2026-06-04일 수도 있음. "어제 대비"라고 단정하면 실제 비교 기준과 어긋날 위험이 있어, 사용자가 즉시 비교 날짜를 확인할 수 있도록 화면에 명시한다.

## 3. 실행 방법 (수동, 안전한 단계)

```bat
.venv\Scripts\python.exe scripts\compare_snapshots.py
```
출력 예시:
```
[compare_snapshots] change dump saved: logs/sidecar/change_dump_latest.json
[compare_snapshots] today=2026-06-04 vs yesterday=2026-06-02: NEW=30 DEP=21 R↑=159 R↓=186 S↑=188 S↓=473 SECTOR=0 TOTAL=1057
[compare_snapshots] done
```
종료 코드 0. 어떤 상황에서도 종료 코드 0 (스냅샷 부족 / JSON 파싱 실패 / 예측 못 한 예외 포함).

### 3-2. 부족 시나리오
daily 스냅샷이 1개 이하인 경우:
```
[compare_snapshots][WARN] daily 스냅샷이 1개뿐입니다 (2개 필요). run_daily.bat 또는 run_sidecar.bat을 하루 1회 이상 더 실행해서 어제 스냅샷을 쌓아주세요. 확인 경로: logs/sidecar/daily/
[compare_snapshots] change dump saved: logs/sidecar/change_dump_latest.json
[compare_snapshots] done
```
이때도 `change_dump_latest.json`은 생성되며 `status: "not_enough_snapshots"`로 화면에 친절한 안내가 표시된다.

### 3-3. 화면 빌드 + 확인
```bat
npm run build
npm run dev
```
브라우저에서 `/` → "2) 후보 점검" → "🔄 어제 대비 변화" → `/changes` 진입.

### 3-4. 추후 자동화 검토
이번 단계에서는 `run_daily.bat`에 통합하지 않는다. 1주간 매일 수동 실행으로 안정성 확인 후 v0.3-8 또는 v0.3-7-hotfix로 `[10/12]` 또는 `[11/12]` 다음에 WARN-only 단계로 통합 검토.


### `change_type` 값 (7종, 1행당 1차 유형)
| 값 | 의미 |
|---|---|
| `NEW` | 오늘 바닥 후보, 어제는 아니었음 |
| `DEPARTED` | 어제 바닥 후보, 오늘은 아님 |
| `RANK_UP` | 양쪽 순위 존재, 오늘 < 어제(개선) |
| `RANK_DOWN` | 양쪽 순위 존재, 오늘 > 어제(악화) |
| `SCORE_UP` | 순위 변화 없음, 점수 ≥ +0.5 |
| `SCORE_DOWN` | 순위 변화 없음, 점수 ≤ -0.5 |
| `SECTOR_CHANGE` | 위 어느 것도 아니지만 sector 필드 변동 |

`sector_changed`는 모든 row에 독립 boolean으로 표시 — 다른 유형이어도 섹터가 바뀌었으면 `true`.

### 데이터 소스
- **순위**: `scan_dump.candidates_bottom[]` 배열의 인덱스+1을 사용 (1-base). 이는 사이드카가 자체적으로 정렬한 우선순위 순서이며, **scan_dump 출력 구조에 그대로 존재하는 정보**다.
- **점수**: `scan_dump.all_stage_labels[].score_from_run_scan` (전체 분석 종목, 약 2,500개에 모두 부여).
- **섹터/단계/이름**: `candidates_bottom` 우선, 없으면 `all_stage_labels`.

> **새 키 요구 0건** — 모든 비교 항목은 v0.2-1부터 존재하던 기존 키만 사용.
