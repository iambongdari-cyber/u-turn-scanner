## 0. 사용자가 정의한 8단계 실제 매매 흐름

```
1. U턴스캐너로 종목을 찾는다.
2. 매수가를 정한다.
3. 키움에서 예약매수를 걸어둔다.       ← 사용자가 직접 (스캐너 미관여)
4. 일상생활을 한다.                       ← 시간 경과
5. 예약매수가 체결되면 보유종목으로 관찰한다.
6. 미리 계산한 목표 매도가가 있지만, 차트 흐름을 보며 매도가를 다시 계산할 수 있다.
7. 추세가 좋으면 눌림목에서 추가매수를 검토한다.
8. 모든 판단과 변경 이유는 기록되어야 한다.
```

→ U턴스캐너의 역할은 **(1)(2) 후보 발견 + 매수가 산정 보조** 와 **(5)~(8) 체결 후 기록·점검·재조정 보조** 양 끝단. 중간 (3)(4) 는 **사용자가 직접 키움에서 처리**하고 스캐너는 관여 0건.

## 3. 매매 상태값 추가 (사용자 명세 §2)

### 3-1. `TradeStatus` enum (8 단계)

```ts
type TradeStatus =
  | 'WATCHING'              // 관찰중      — 아직 예약 안 걸음
  | 'RESERVED'              // 예약매수 대기 — 키움 예약 걸어둠
  | 'FIRST_FILLED'          // 1차 체결    — 1차 매수가 체결됨
  | 'SECOND_FILLED'         // 2차 체결    — 2차 매수가도 체결 (자동으로 HOLDING 으로도 분류)
  | 'HOLDING'               // 보유중       — (1차 또는 2차 체결 후 일반 보유 상태)
  | 'PARTIAL_SOLD'          // 일부매도    — 목표 매도가 도달 후 일부 차익실현
  | 'CLOSED'                // 매도완료    — 전량 매도 완료
  | 'CANCELLED';            // 취소         — 예약 취소 또는 계획 폐기
```

### 3-2. 상태 전이도

```
                  관찰중 (WATCHING)
                      │
                      ▼  (사용자가 키움에서 예약 걸었음 선택)
                  예약매수 대기 (RESERVED)
                  ┌───┴───────────────────┐
            (체결) │                   (취소) │
                  ▼                          ▼
            1차 체결 (FIRST_FILLED) ─────► 취소 (CANCELLED)
                  │
                  ▼ (자동 → HOLDING 으로도 분류)
            보유중 (HOLDING) ◄───── 2차 체결 (SECOND_FILLED)
                  │
                  ▼ (사용자가 일부 매도)
            일부매도 (PARTIAL_SOLD)
                  │
                  ▼ (전량 매도)
            매도완료 (CLOSED)
```

### 5-3. AI 판단 3 단계 매핑

```ts
type ReservationVerdict = 'KEEP' | 'CANCEL' | 'REVIEW';

function buildReservationOpinion(
  plan: TradePlan,
  currentPrice: number,
): ReservationOpinion {
  const diff1 = (currentPrice - plan.first_buy_price) / plan.first_buy_price * 100;
  const diff2 = plan.second_buy_price
    ? (currentPrice - plan.second_buy_price) / plan.second_buy_price * 100
    : null;

  // (1) 현재가가 1차 예약가 위 +5% 이상 = 멀어짐 → 가격 재검토
  if (diff1 > 5) {
    return {
      verdict: 'REVIEW',
      verdict_label: '가격 재검토',
      reason: `현재가가 1차 예약가 대비 +${diff1.toFixed(1)}% 이미 상승. 예약가 재산정 고려.`,
      today_actions: [
        '예약가 상향 또는 진입 포기 검토',
        '뒤늦은 추격 금지',
        '눌림목 기다릴지 결정',
      ],
    };
  }

  // (2) 손절가 이미 이탈 → 예약 취소
  if (currentPrice <= plan.stop_loss_price) {
    return {
      verdict: 'CANCEL',
      verdict_label: '예약 취소',
      reason: `현재가가 손절 기준가(${plan.stop_loss_price.toLocaleString()}원) 이미 이탈. U턴 실패 가능성.`,
      today_actions: [
        '키움에서 예약 즉시 취소',
        '카드에서 [취소] 클릭 + 취소 사유 기록',
        '추가 진입 보류',
      ],
    };
  }

  // (3) 그 외 = 예약 유지
  return {
    verdict: 'KEEP',
    verdict_label: '예약 유지',
    reason: `현재가 ${currentPrice.toLocaleString()}원 — 예약가 근처. U턴 신호 유지 중.`,
    today_actions: [
      '키움에서 예약 유지 확인',
      '시초가/장중 변동성 큰 경우만 재검토',
      '체결되면 카드에서 [1차 체결] 클릭',
    ],
  };
}
```

function calculateAvgBuyPrice(plan: TradePlan): number {
  const p1 = plan.actual_first_filled_price ?? plan.first_buy_price;
  const p2 = plan.actual_second_filled_price ?? plan.second_buy_price;

  if (plan.status === 'FIRST_FILLED') return p1;
  if (plan.status === 'SECOND_FILLED' || plan.status === 'HOLDING') {
    // 단순 평균 — 수량 정보 없이 가정 (수량은 v0.4.1+ 에서 도입)
    return p2 ? (p1 + p2) / 2 : p1;
  }
  return p1;
}

```ts
function evaluateAddBuy(
  plan: TradePlan,
  currentPrice: number,
  scan?: ScanCandidate,
): AddBuyCheck {
  const ma60 = scan?.ma60 ?? null;
  const recent_volume = scan?.recent_volume ?? null;
  const avg_volume = scan?.avg_volume ?? null;

  // ① 1차 매수가 위에서 유지
  const above_first_buy = currentPrice >= plan.first_buy_price;

  // ② 거래량 급감 없이 눌림 (최근 거래량 ≥ 평균 거래량의 70%)
  const volume_holding = (recent_volume && avg_volume)
    ? recent_volume >= avg_volume * 0.7
    : false;

  // ③ 60일선 또는 지지선 이탈 없음
  const support_holding = ma60 ? currentPrice >= ma60 * 0.97 : false;

  // ④ 총 투자금 한도 초과 없음 — v0.4 에서는 사용자 수동 체크 (한도 정보 없으므로)
  const within_budget = true; // 기본 true, 사용자가 수동 false 가능

  const passed_count = [above_first_buy, volume_holding, support_holding, within_budget]
    .filter(Boolean).length;

  let verdict: AddBuyCheck['verdict'];
  let reason: string;

  if (passed_count === 4) {
    verdict = 'BUY_MORE_OK';
    reason = '4 조건 모두 충족. 2차 매수가 근처 눌림 시 추가매수 검토 가능.';
  } else if (passed_count >= 2) {
    verdict = 'BUY_MORE_WAIT';
    reason = `${passed_count}/4 조건 충족. 추가매수는 보류 — 2차 매수가 근처 눌림 확인 필요.`;
  } else {
    verdict = 'BUY_MORE_NO';
    reason = `${passed_count}/4 조건만 충족. 추가매수 금지. 추세 회복 확인 후 재검토.`;
  }

  return {
    evaluated_at: nowISO(),
    conditions: { above_first_buy, volume_holding, support_holding, within_budget },
    passed_count,
    verdict,
    reason,
  };
}
```

## 15. 주의사항

### 15-1. 키움 예약매수는 사용자가 직접 (사용자 명세 §9)
- 스캐너는 (1)(2) 후보 발견 + 매수가 산정 보조
- 스캐너는 (5)~(8) 기록 + 점검 + 재조정 보조
- 중간 (3)(4) 키움 예약매수 + 일상 = **사용자 영역**, 스캐너 관여 0건

### 15-2. 체결 여부 사용자 수동 입력
- 키움 API 미사용 → 자동 감지 불가
- 사용자가 매일 카드의 [1차 체결] / [2차 체결] / [취소] 버튼 클릭
- 실제 체결가도 사용자가 직접 입력 (`actual_first_filled_price`)
- 입력 안 하면 `WATCHING` / `RESERVED` 상태 유지 (자동 변경 없음)

### 15-3. 변경 이유 필수 강제
- 목표가 / 손절가 변경 모달에서 이유 빈 칸이면 [변경 기록] 버튼 비활성
- 사용자 명세 §8 "모든 판단과 변경 이유는 기록되어야 한다" 준수
- 추천 칩 클릭으로 빠른 입력 가능 + 자유 수정 가능

### 15-4. 추가매수 4 조건 — 4번째는 사용자 수동 체크
- `within_budget` (총 투자금 한도) 은 사용자가 직접 입력
- 스캐너가 총 투자금 정보를 모르므로 기본 `true`, 사용자 토글 가능
- v0.4.1+ 에서 한도 입력 기능 도입 시 자동화

### 15-5. localStorage 용량 — 모든 변경 이력 누적
- `target_change_history[]` + `stop_loss_change_history[]` 매번 누적
- localStorage 한계 5MB 도달 우려 적음 (한 종목당 ~2KB × 100종목 = ~200KB)
- 그래도 v0.5+ Supabase 마이그레이션 권장

### 15-6. 8 상태 외 상태 추가 금지
- 사용자 명세 §2 8 단계 외 자체 상태 추가 X
- 향후 사용자 요청 시 추가

### 15-7. AI 판단 변경 종목 추적 (GPT §5)
- 어제 vs 오늘 AI 판단 비교는 어제 snapshot 필요
- `daily/snapshot_yyyymmdd.json` 의 trade_plans 와 비교 (3차 archive_sidecar.py 활용)
- 어제 데이터 없으면 §5 섹션 생략

### 15-8. 카드 모달 vs 별도 페이지
- 5차의 모든 추가는 카드 안 영역 또는 모달 → 별도 페이지 분리 X (v0.4.1 에서 분리)

### 15-9. 예약매수 대기 → 1차 체결 자동 분류
- `RESERVED` → `FIRST_FILLED` 변경 시 카드가 자동으로 "예약매수 대기" 섹션에서 "보유종목 점검" 섹션으로 이동
