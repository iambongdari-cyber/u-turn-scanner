## 1. 현재 `run_daily.bat` 구조 분석

### 9단계 흐름 요약 (v0.2.1까지 적용 상태)

| 단계 | 명령 | 실패 정책 | 주요 출력 |
|------|------|-----------|-----------|
| **[1/9] 종목 마스터 갱신** | `load_stocks.py --market ALL --stocks-only` | **WARN** (계속) | stocks 갱신 |
| **[2/9] 일봉 갱신** | `load_stocks.py --prices-only --gap-fill --min-cap 800 --workers 8 --fast-ticker-index --log-file logs\run_daily.log` | **HARD** (멈춤) | daily_prices 갱신, **이 단계 직후 `logs\_price_cache.pkl` 삭제** |
| **[3/9] 시장 지수** | `load_indices.py` | **HARD** | market_indices |
| **[4/9] 뉴스 리스크** | `load_news_risks.py` | **HARD** | news_risks |
| **[5/9] 일일 스캔** | `run_scan.py --report-type daily --use-price-cache` | **HARD** | reports + scan_results (daily). **가격 캐시 첫 빌드** |
| **[6/9] 주간 스캔** | `run_scan.py --report-type weekly --use-price-cache` | **HARD** | reports + scan_results (weekly). **가격 캐시 재사용** |
| **[7/9] 백테스트** | `run_backtest.py` | **WARN** | backtest_results |
| **[8/9] 알림 생성** | `generate_alerts.py` | **WARN** | alerts |
| **[9/9] 웹 서버** | `npm run dev`(별도 창) + 브라우저 자동 오픈 | — | 사용자 진입 |

### 각 단계가 하는 일과 주의점
- **[2]는 가격 캐시 무효화 트리거**: 일봉 행이 바뀐 후 옛 캐시를 즉시 삭제해, [5]가 캐시를 새로 빌드하도록 보장.
- **[5]·[6]은 사이드카가 재사용할 캐시를 만드는 단계**: `fetch_all_prices(use_cache=True)`로 [5]가 캐시 빌드, [6]이 캐시 히트.
- **[7] 백테스트는 캐시를 쓰지 않는다**(`--use-price-cache` 옵션 미사용). 사이드카 캐시 효율과 독립.
- **[8]·[9]는 WARN 또는 종착**: 사이드카가 이 흐름에 들어가도 멈춰서는 안 되는 정책 기준.

### 사이드카를 어디에 넣는 것이 안전한가 (요약)
- 사이드카는 `fetch_all_prices(use_cache=True)`를 통해 캐시를 활용 → **[5]가 캐시를 빌드한 이후** 위치가 가장 효율적.
- 사이드카 실패가 전체 배치를 멈추면 안 됨 → **WARN 정책을 쓰는 [7]·[8]과 같은 영역**에 배치하는 것이 자연스러움.
- 사이드카 결과(`logs/sidecar/*.json`)는 화면(`/bottom-watch`·`/leaders` 등)이 읽는다. 사용자가 웹 진입 직후 라벨을 보려면 **[9] 웹서버 시작 전**에 JSON이 만들어져 있어야 함.

→ 위 3가지 조건을 동시에 만족하는 위치가 가장 안전. 자세한 후보 분석은 2절.

## 3. 권장 삽입 위치: **후보 B (일일·주간 스캔 후 / 백테스트 전)**

### 5가지 관점 종합 평가
- **캐시 재사용:** [5]가 캐시를 빌드해 [6]이 히트, 그 직후 사이드카 2개도 히트 → **거의 부담 없음**(추정 1~3분).
- **실패 격리:** 양옆이 마지막 HARD 단계와 첫 WARN 단계 → 사이드카를 WARN으로 두기에 가장 일관된 위치.
- **화면 데이터 최신성:** 사용자가 [9] 웹서버 진입 시점에 사이드카 JSON이 **오늘자**로 완성되어 있음.
- **실행 시간 증가:** 사이드카 2회 ≈ 1~3분 추가. 전체 28~30분대 → 30~33분대 정도(현 데이터 기준).
- **9단계 안정성:** 단계 번호 재정렬 외에 흐름·실패정책 변화 없음. 의미적 응집도 유지.

→ **5가지 기준 모두 최선** → 후보 B 채택.

## 5. 실패 처리 정책

### 핵심 원칙
**사이드카 실행 실패가 `run_daily.bat` 전체를 멈추면 안 된다. 웹서버([11/11])는 반드시 떠야 한다.**

이 원칙은 v0.2-1·v0.2-2에서 화면이 graceful 처리되도록 설계한 것과 일관된다(JSON 없으면 화면이 안내만 표시하고 정상 동작).

### 정책 표

| 사건 | 처리 |
|------|------|
| **[7/11] scan_dump 실패** | 화면에 `[WARN]` 출력 + `run_logger.py step ... WARN`으로 로그에 기록 + **[8/11]로 진행** |
| **[8/11] sector_dump 실패** | 동일하게 `[WARN]` + 로그 + **[9/11]로 진행** |
| **두 사이드카 모두 실패** | 각각 WARN, 배치 계속. 웹서버 정상 기동. 화면은 graceful 안내 표시(현재 구현 그대로) |
| **사이드카 실행 중 파이썬 예외** | sys.exit 호출 시 errorlevel=1. `if errorlevel 1` 분기에서 WARN 로그만 남기고 `goto :end` 하지 **않음** |
| **로그 파일 자체 기록 실패** | 무시(이미 사이드카 스크립트에서 try/except로 처리). 화면 graceful로 보완 |
| **JSON 파일이 잘못 생성됨** | 화면에서 parse_error로 graceful 처리(v0.2-2 구현). 배치 진행에는 영향 없음 |

### 화면 측 안전망 (이미 구현됨)
- `app/_lib/sidecar.ts`: JSON 부재/파싱 실패 모두 흡수
- `/bottom-watch`·`/leaders`: 빈 상태/오류 상태 graceful 표시
- `/kiwoom-helper`·`/journal`: 사이드카 부재 시 작은 안내만 표시하고 기본 화면 정상

### 화면이 "어제 JSON"을 그대로 쓰는 시나리오 처리
- 사이드카 실패 시 **이전 실행에서 만든 `logs/sidecar/*.json`이 그대로 남아있음** → 화면은 **어제 분석**을 그대로 표시
- 사용자가 라벨이 오늘자가 아니라는 사실을 모를 수 있음 → **JSON의 `generated_at` 필드를 화면 상단에 항상 노출**(v0.2-2/3 이미 구현됨). 이 필드의 날짜로 사용자가 신선도를 판단 가능.

### 단계 실행 명령 패턴 (개념)
```bat
echo [7/11] 바닥/단계 사이드카 생성 (scan_dump.py)...
"%PY%" scripts\scan_dump.py
if errorlevel 1 (
    echo.
    echo [WARN] scan_dump 사이드카 생성 실패. 이전 JSON으로 화면 표시 가능. 계속 진행.
    echo   [7] 바닥 사이드카: 실패-계속진행>>"%LOGFILE%"
) else (
    echo   [7] 바닥 사이드카: 성공>>"%LOGFILE%"
)
echo.

echo [8/11] 섹터 사이드카 생성 (sector_dump.py)...
"%PY%" scripts\sector_dump.py
if errorlevel 1 (
    echo.
    echo [WARN] sector_dump 사이드카 생성 실패. 이전 JSON으로 화면 표시 가능. 계속 진행.
    echo   [8] 섹터 사이드카: 실패-계속진행>>"%LOGFILE%"
) else (
    echo   [8] 섹터 사이드카: 성공>>"%LOGFILE%"
)
echo.
```

> **CRLF 주의:** 위 패턴은 기존 [1/9] 종목 마스터(WARN)·[7/9] 백테스트(WARN)·[8/9] 알림 생성(WARN)과 **동일 구조**라 검증된 패턴. 새로운 batch 문법 도입 없음.

## 6. 실행 시간 영향 분석

### 사이드카 단독 실행 시간 추정 (캐시 히트 시)
- `scan_dump.py`: `analyze()`를 모든 종목에 호출하지만 캐시 히트로 일봉 로드는 즉시. 종목 2,500개 분석 + JSON 직렬화. **추정 1~2분.**
- `sector_dump.py`: `analyze()` 미호출, 종목별 metric 계산(20일 수익률·평균 거래대금·전고점 위치 등)만. **추정 30초~1분.**
- 합계: **약 1.5~3분 추가.**

### 캐시 충돌 가능성 분석
| 단계 | 캐시 조작 |
|------|----------|
| [2/11] 일봉 갱신 | **캐시 삭제**(`del logs\_price_cache.pkl`). 다음 단계가 빌드 |
| [3/11]~[4/11] | 가격 미사용 |
| [5/11] 일일 스캔 | **캐시 빌드**(첫 빌드, DB → 캐시 저장) |
| [6/11] 주간 스캔 | 캐시 히트 |
| **[7/11] scan_dump** | 캐시 히트(가장 따뜻함) |
| **[8/11] sector_dump** | 캐시 히트(여전히 유효) |
| [9/11] 백테스트 | 캐시 미사용(자체 fetch) |
| [10/11] 알림·[11/11] 웹서버 | 가격 미사용 |

**충돌 위험:** 없음. 사이드카 2개 모두 `use_cache=True`로 캐시를 **읽기만 함**. 캐시 파일 동시 쓰기 충돌 시나리오 0건.

### 캐시 히트가 가장 좋은 위치
**[6/11]과 [9/11] 사이.** 이 구간에서는 캐시가 빌드 직후 상태로 따뜻하고, 백테스트가 캐시를 무효화하지 않는다. 후보 B와 일치 → 권장 위치 재확인.

### 전체 실행 시간 예측
- 현재 약 28~30분
- v0.3 적용 후: **약 30~33분** (사이드카 ~3분 추가)
- 사용자가 매일 마주하는 추가 부담은 적정 수준

## 7. CRLF 보호 절차 (v0.3 작업의 핵심 위험)

### 배경
`run_daily.bat`은 Windows 배치 파일로, **줄바꿈이 CRLF여야 cmd가 정상 파싱**한다. 과거 한 번 LF로 변환된 적이 있어 **창이 즉시 닫히는 사고**가 발생함. v0.3에서 절대 재발 방지해야 함.

### 작업 전 백업
```bat
copy run_daily.bat run_daily.bat.before_v0.3
```

### 편집 도구 영향
- **Edit 도구**: 일부 라인만 치환할 때 주변 CRLF를 보존하는 경향. v0.2-3에서 이 패턴으로 성공.
- **Write 도구**: 파일 전체를 새로 작성. LF로 떨어지는 경향 있어 위험. **v0.3에서는 Write 사용 금지** 권장.

→ **권장:** Edit 도구로 **타깃이 명확한 4~6개 치환**으로 끝낸다.
  - 치환 항목:
    1. 단계 번호 `[N/9]` → `[N/11]` (9곳)
    2. 사이드카 2개 단계 삽입(주간 스캔 후, 백테스트 전)
    3. 종료 요약 텍스트의 `9단계` 표현 보정(있다면)

### 편집 후 검증 (필수)
1. **CRLF 확인**:
   ```bat
   .venv\Scripts\python.exe -c "d=open('run_daily.bat','rb').read(); print('CRLF count:', d.count(b'\r\n')); print('lone LF count:', d.count(b'\n') - d.count(b'\r\n'))"
   ```
   - 정상: `CRLF count`가 줄수와 거의 일치, `lone LF count`는 0
2. **수정만 비교**:
   ```bat
   git diff --ignore-cr-at-eol --stat run_daily.bat
   ```
   - 실제 의도된 줄 수 변경만 나타나야 함(사이드카 단계 추가 줄수 + 단계 번호 치환 줄수)
3. **로컬 실행 검증**(가장 중요):
   - `run_daily.bat`을 더블클릭 → 창이 즉시 닫히면 LF 사고 → 즉시 롤백
   - 정상이라면 11단계가 모두 표시되고 마지막에 `Done:` 출력 후 사용자 입력 대기까지 도달

### 만약 LF로 변환되었다면 (응급)
```bat
.venv\Scripts\python.exe -c "d=open('run_daily.bat','rb').read().replace(b'\r\n',b'\n').replace(b'\n',b'\r\n'); open('run_daily.bat','wb').write(d)"
```
이전부터 사용해 온 CRLF 정규화 한 줄. v0.3 작업 직후에도 같은 명령을 무조건 적용 → 한 번 더 안전망.

### 재발 방지 절차 (체크리스트)
- [ ] 작업 전 `copy run_daily.bat run_daily.bat.before_v0.3`
- [ ] 편집은 **Edit 도구로 타깃 치환만**
- [ ] 편집 직후 CRLF 정규화 명령 1회 적용
- [ ] `git diff --ignore-cr-at-eol --stat run_daily.bat`로 실내용 변경만 나타나는지 확인
- [ ] 더블클릭 1회 테스트
- [ ] OK 확인 후 커밋

## 10. 로그 기록 방식

### 현재 `run_logger.py` 활용
`run_daily.bat`은 이미 `run_logger.py`를 통해 `logs/run_daily.log`에 단계별 성공/실패를 기록한다. 같은 메커니즘을 그대로 사용.

### 사이드카 단계의 로그 표기 (제안)
```

[7] 바닥 사이드카: 실패-계속진행
[8] 섹터 사이드카: 성공
[8] 섹터 사이드카: 실패-계속진행
```
- 기존 [1] 종목 마스터(WARN)·[7] 백테스트(WARN)·[8] 알림(WARN) 패턴과 완전 동일.

### 사이드카 스크립트 자체의 출력
- `scan_dump.py`·`sector_dump.py`는 콘솔에 진행 상황을 print함. 그 출력을 따로 파일에 저장할 필요는 없음(콘솔 창에서 사용자가 직접 확인).
- 만약 자동 기록을 원하면 `>> logs\run_daily.log 2>&1` 같은 redirection은 **인코딩 문제 위험**(한글 출력) → **비권장**.

### 실패 시 ERROR vs WARNING 처리
- **WARNING으로 처리**(이미 5절에서 정책 확정).
- `[ERROR]`는 배치 중단을 암시하지만, 사이드카는 중단하면 안 됨 → **`[WARN]`**으로만.

## 보고서 최종 판단

### 1. `run_daily.bat`에 바로 통합해도 되는가?
- **권장하지 않음.** 먼저 별도 `run_sidecar.bat`을 만들어 **표준 실행 패턴을 검증**한 뒤, 그 결과를 토대로 `run_daily.bat`에 끼우는 것이 안전.
- 사이드카가 단독 환경에서 매일 안정적으로 도는 것을 1주 정도 확인한 후 통합이 가장 사고 적음.

### 2. 먼저 `run_sidecar.bat` 별도 배치부터 만드는 것이 나은가?
- **예.** 강력 추천. 이유:
  - CRLF 위험을 작은 새 파일에서 먼저 익숙해질 수 있음(기존 9단계 손대지 않음)
  - 사이드카 실행 시간·실패 빈도를 실측해서 통합 시 신뢰성 있게 설계 가능
  - 통합 실패 시 사용자가 수동으로 돌리는 절차의 **표준 대체재** 역할도 함

### 3. 9단계 유지 vs 11단계 확장?
- **11단계 확장 권장.** 이유:
  - 위치 B를 채택하면 사이드카가 [7]·[8] 자리에 들어가야 의미적으로 정확
  - 사용자가 "지금 몇 번째 단계인가"를 정확히 인지
  - `8A/8B` 같은 보조 표기는 의미가 모호하고 디버깅·로그 가독성에 손해

### 4. 실패 처리 정책
- **사이드카 2개 모두 WARN-only.**
- `if errorlevel 1 ( ... )` 분기에 `goto :end`를 **절대 넣지 않음.**
- `run_logger.py` 기존 패턴 그대로 `실패-계속진행` 텍스트로 기록.
- 화면이 graceful로 받쳐주므로(이미 구현됨) JSON 부재/이전 JSON 잔류 시에도 사용자 경험 깨지지 않음.

### 5. v0.3 개발을 진행해도 되는가?
- **조건부 진행 가능.** 아래 안전 순서를 지키면 위험이 매우 낮음.
- 진행 전 사용자 승인 + 백업 + CRLF 보호 절차 + 결과 동일성 검증 절차 적용이 전제.

### 6. 진행한다면 가장 안전한 개발 순서

**Phase A — 사이드카 별도 배치 도입 (위험 매우 낮음)**
1. `run_sidecar.bat` 작성(단순 2단계 + CRLF 확인)
2. CRLF 확인 + 단독 실행 1회 성공
3. 3~7일 매일 단독 실행해 사이드카 안정성 측정 (실패율·평균 실행시간)

**Phase B — 통합 작업 직전 점검**
4. 백업: `copy run_daily.bat run_daily.bat.before_v0.3`
5. 사전 검증 스냅샷: `check_db.py` 출력 보관 + `scan_results`(daily/weekly TOP) export

**Phase C — `run_daily.bat` 통합 (조심)**
6. Edit 도구로 단계 번호 `[N/9]` → `[N/11]` 일괄 치환(9곳)
7. Edit 도구로 [6/11] 종료 줄과 [7/11] 백테스트 시작 사이에 신규 `[7/11] 바닥 사이드카`·`[8/11] 섹터 사이드카` 블록 삽입 (정책: WARN, 기존 [1]/[7]/[8] 패턴 그대로)
8. 종료 요약 텍스트 안내 보정(필요 시)
9. CRLF 정규화 명령 1회 무조건 적용
10. `git diff --ignore-cr-at-eol --stat run_daily.bat`로 실내용 변경 검토

**Phase D — 실행 검증**
11. `run_daily.bat` 더블클릭 → 창이 즉시 닫히면 즉시 롤백
12. 정상 진행 시 끝까지 도달 확인 (`Done:` 출력 + 사용자 입력 대기)
13. `logs/run_daily.log` 확인 — 11단계 모두 기록되었는지
14. `check_db.py` 사후 출력 → 사전과 비교 (`reports`/`scan_results`/`backtest_results` 행수 동일)
15. `/bottom-watch`·`/leaders` 화면 진입 → 오늘자 `generated_at` 표시 확인

**Phase E — 커밋·푸시**
16. `git add run_daily.bat docs/V0.3_DESIGN.md docs/V0.3_REPORT.md`
17. `git commit -m "feat(v0.3): run_daily.bat에 사이드카 2개 자동 통합 (11단계, WARN-only)"`
18. `git push`

**Phase F — 1주 안정성 모니터링**
19. 매일 실행 결과 모니터링. `logs/run_daily.log` 확인.
20. 이상 발견 시 즉시 롤백(11절 기준).
