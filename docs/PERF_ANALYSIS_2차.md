## 1. 병목 원인 정밀 분석

핵심: **`daily_prices` 전체(약 686,660행)를 세 번 따로 로드**한다. 세 단계가 각각 독립 파이썬 프로세스라 메모리를 공유하지 못한다.

| 단계 | 동작 | 비고 |
|------|------|------|
| ⑤ 일일 스캔 | `run_scan.py` `fetch_all_prices()`(147행)로 **전체 로드(1회)** | 날짜 필터 없음. 1,000행/요청 → 약 686회 요청 |
| ⑥ 주간 스캔 | 동일 데이터를 **전체 재로드(2회째)** | 일일과 차이는 골든크로스 윈도우 5 vs 10뿐. **로드 데이터는 100% 동일** |
| ⑦ 백테스트 | `run_backtest.py` `fetch_all_prices()`(106행)로 **전체 재로드(3회째)** | + 시뮬레이션 약 6분 15초 |

추가로, 백테스트(⑦)는 reports **148개 전부(scan_results 1,583쌍)를 매 실행마다 재시뮬**한다. 그러나 **이미 청산된 포지션(약 893건)은 과거 구간이 고정이라 결과가 절대 바뀌지 않는다** → 재계산이 낭비. 시뮬 6분 15초의 상당 부분이 여기에 쓰인다. (OPEN 포지션은 약 690건)

### 분석에 실제로 필요한 이력 기간 (가장 중요한 발견)
`run_scan.py`의 `analyze()`(248행~)는 항상 **최신일(t = n-1)만** 평가한다. 가장 멀리 보는 계산은 "최근 60일 U턴 검증"(`days_below_ma60`, 311~313행)이며, 그 60일 각각에 `ma60`(60일 롤링, 260행)이 유효해야 한다.

- `ma60`은 60일 롤링 → 60일 전부터 유효
- 최근 60일 U턴 윈도우의 가장 이른 날에도 `ma60`이 유효하려면 → **약 120거래일** 필요
- ichimoku(`span_b`)는 약 78일, 그 외(골든크로스 윈도우·`recent_high_60`·`avg_value_20` 등)는 60일 이내

**결론: 최근 약 120거래일만 있으면 `analyze()` 결과가 완전히 동일하다.** 현재는 종목당 약 271거래일(전체 686,660행)을 로드하고 있어, 절반 이상이 분석에 쓰이지 않는다.

## 2. 개선 후보 평가 (A~D)

### A. 분석에 필요한 최근 N일만 로드 — ✅ 안전(조건부)
- **결과 영향:** N ≥ **120거래일**이면 `analyze()`가 그 이상 과거를 참조하지 않으므로 **TOP10 동일**. 여유를 두고 약 150거래일(대략 `date >= 기준일 - 220일`) 권장.
- **효과:** 스캔 1회 로드 271일 → 150일 ≈ **행·요청 약 45% 감소**.
- **건드리는 파일:** `run_scan.py`의 `fetch_all_prices()`에 **날짜 필터만** 추가(점수/매매 로직 불변).
- **주의:** `replay_history.py`(과거 리포트 재생)는 과거 날짜 기준이므로, 필터를 "기준일 − 약 150거래일"로 일반화해야 과거 재생이 깨지지 않는다. 단순히 "오늘 − N일" 고정으로 넣으면 안 됨.

### B. 일일·주간 스캔 로드 공유 — ✅ 가장 안전 + 효과 큼
- **결과 영향:** 두 스캔은 **같은 데이터를 두 번** 로드한다. 한 번 로드해서 윈도우 5·10 둘 다 분석하면 로드만 1회로 줄고, 분석 로직·데이터가 그대로라 **결과가 자명하게 보존**된다.
- **효과:** 스캔 로드 **2회 → 1회(절반)**.
- **건드리는 파일:** `run_scan.py`(한 번 로드 후 두 리포트를 생성하는 모드 추가) + `run_daily.bat`(⑤⑥ 두 줄 → 한 줄). 9단계의 "스캔" 의미는 유지.

### C. 백테스트 최적화 — ⚠️ 효과 가장 크나 손이 더 감
- **결과 영향:** 이미 청산된 포지션은 재시뮬 불필요(결과 불변). **OPEN(약 690) + 신규 리포트만 재시뮬**하면 됨. 청산분은 기존 `backtest_results` 값을 그대로 유지(재기록 안 함) → 안전.
- **효과:** 시뮬 6분 15초와 로드 범위 모두 크게 감소(최대 효과).
- **건드리는 파일:** `run_backtest.py` **로직 변경**(기존 청산 결과를 읽어 건너뛰기). A·B보다 신중·검증이 더 필요.

### D. 가장 안전하게 시간만 줄이는 방법 — 추천 순서
1. **B (스캔 로드 공유)** — 결과 보존 자명, 스캔 로드 절반. **1순위**
2. **A (최근 ~150일 로드)** — 결과 동일(N≥120), 로드량 약 45%↓. replay 호환만 챙기면 안전. **2순위**
3. **C (백테스트 청산분 건너뛰기)** — 효과 최대지만 로직 변경이라 가장 신중. **3순위**

**(별도 저위험 옵션)** `fetch_all_prices`의 페이지 크기(현재 1,000행/요청)를 키워 요청 횟수를 줄이는 방법 — 데이터/결과 불변. 단 Supabase의 `max-rows` 설정에 좌우되므로 효과는 테스트로 확인 필요(서버가 1,000행으로 제한하면 이득 없음).

## 4. 결과 동일성 검증 방법 (적용 시 필수 절차)

1. 개선 적용 **전**: 현재 기준일의 `scan_results`(daily·weekly TOP)와 `backtest_results` 스냅샷을 보관(또는 export).
2. 개선 적용 **후**: 같은 기준일로 재실행.
3. 비교:
   - 스캔: 각 리포트의 `(ticker, rank, score, final_grade)`가 **완전 일치**하는지.
   - 백테스트: 동일 `(report_id, ticker)`의 결과 값이 청산분에서 **불변**인지.
4. **1종목이라도 달라지면 즉시 롤백.** (각 개선은 옵션/플래그로 켜고 끌 수 있게 만들어 롤백을 보장)
